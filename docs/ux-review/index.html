02 / Detailed review

Where the experience breaks down.

Priorities reflect likely task impact and breadth. These are expert findings, not measured user failure rates.

Read this as an evolution of the existing portal. Keep the setup workbench, reusable presets, track imagery, light/dark themes, destructive-action confirmations, URL-backed queue selection, and move-up/down controls. Improve the gaps around them.

12 findings · Expand a row for evidence and acceptance criteria.

P1 · 01

Secondary text is too faint to carry essential information

Visual hierarchy · verified in browser and design tokens

Observed → impact

Track metadata, helper text, status labels, and timestamps use text-dim. The token measures 3.15:1 on the dark card surface and 3.20:1 on white. Small, meaningful text needs 4.5:1 under WCAG contrast guidance. Body weight is 300; “bold” resolves to 500, weakening hierarchy further.

Proposed change

Reserve dim styling for decoration. Use accessible secondary text, normal body weight 400, and genuine 600–700 headings. Keep 14px for dense tables; use 15–16px for reading and forms. Increase contrast without making every surface brighter.

Done when: meaningful normal-size text reaches ≥4.5:1 in both themes, including translucent chips and image overlays. Verify the actual rendered colors; token checks alone do not establish conformance.

Evidence: webapp/src/style.css:38–56, 86–98; FormRow.vue:19; dashboard and setup form at 1280×720. Ratios calculated from the source hex values using WCAG relative luminance.

P1 · 02

Dialogs leave keyboard users on the page behind them

Accessibility · reproduced with Escape and Tab

Observed → impact

Opening “New race setup” leaves focus on its trigger. Escape does not close it; Tab moves into the library search behind the overlay. Modal and Sheet declare dialog roles but have no accessible title binding, focus entry, containment, or return. Mobile More has the same missing focus behavior.

Proposed change

Fix the shared overlay primitives first, following the WAI dialog pattern. Prefer native <dialog> if it preserves nested picker behavior; otherwise add one shared focus implementation. Connect the visible title and keep the background inert.

Done when: focus enters the dialog, Tab/Shift+Tab stay inside, Escape requests a safe close, and closing restores the trigger. Test a picker opened from an editor and confirmation opened over a dirty form.

Evidence: webapp/src/components/ui/Modal.vue, Sheet.vue, webapp/src/App.vue:320–390. Browser reproduction: New race setup → Escape → Tab focuses the underlying search field.

P1 · 03

Closing an editor bypasses the existing unsaved-change guard

Error prevention · source-confirmed

Observed → impact

The guard covers route leave and browser unload. The setup sheet’s close icon, backdrop, and Cancel directly set its open flag to false. Reopening Create resets the draft. A group-only edit is also absent from the editor’s dirty comparison. Users can lose work without the existing warning.

Proposed change

Route every dismissal through the same dirty check, including group changes. Reuse the existing confirmation store: “Discard this race setup?” with “Keep editing” as the safe action. Clean forms close immediately. Extend the workbench’s existing draft behavior only where repeated interruptions justify it.

Done when: changing one field or only its group then clicking X, backdrop, Cancel, Escape, or another route gives consistent protection; choosing Keep editing preserves the values.

Evidence: webapp/src/lib/useUnsavedGuard.ts; webapp/src/pages/Events.vue:117–142, 513–524; sibling close handlers in Dashboard.vue, Queue.vue, and ServerDetail.vue. Draft loss inferred from these handlers; no saved records were changed.

P1 · 04

Readiness and running labels can contradict each other

System status · two contradictions observed

Observed → impact

Race Control showed “Stopped” and “In progress” for its queued event at the same time. The latter only checks started_at. The setup workbench showed “Ready to run” alongside “Save a race setup first” and a disabled Start button. Global installation readiness is being presented as readiness of this particular race.

Proposed change

Use explicit, shared definitions for server state, connection freshness, queued-event state, and launch readiness. Show “Server configured” for global readiness; show “Ready to start” only when the selected instance and saved race meet the start conditions. Present stopped historical entries as pending/interrupted according to backend semantics.

Done when: identical fixtures for stopped-with-start-timestamp, running, empty queue, repeat mode, incomplete draft, and stale connection produce consistent labels on Dashboard, Run Plan, Race Control, and Setup.

Evidence: webapp/src/pages/ServerDetail.vue:1650; Queue.vue:65–67 already checks running state; SetupWorkbench.vue:557–558, 618. Both contradictions observed in the local browser.

P1 · 05

Some visible next steps lead to pages the role cannot use

Task completion · source-confirmed, role testing required

Observed → impact

Dashboard’s “Set up a race” is shown to operators but links to the admin-only setup workbench. The router sends non-admin users back to Dashboard. “Add an instance” in the no-server state is not admin-gated either. A steward can be offered an action that silently returns them to the same place.

Proposed change

Send stewards to Race Setups or the selected server’s Run Plan. Keep installation and instance creation with admins. Viewers should get an explanation when administrator action is needed. Use a visible access explanation for a forbidden deep link rather than an unexplained redirect.

Done when: admin, steward, and viewer can follow every visible empty-state CTA to a permitted, useful destination; forbidden direct links explain the limitation.

Evidence: webapp/src/pages/Dashboard.vue:328–339, 424–427, 508–511; webapp/src/router.ts marks /setup and instance settings admin-only. Browser session was admin; steward/viewer behavior was traced in source.

P1 · 06

Visible form labels are not consistently connected to controls

Accessibility · browser tree and shared components

Observed → impact

The race editor’s Group, Event name, and preset fields render visually labelled but unnamed in the accessibility tree. FormRow’s optional forId is omitted throughout RaceSetupEditor. Hints are not connected with aria-describedby. The custom combobox handles arrows but omits combobox/listbox roles and selection announcements.

Proposed change

Give controls stable IDs and real label associations; connect hint and error text. Complete the existing combobox’s accessible state and active option behavior using the WAI combobox pattern. Keep the existing input components and native selects where search is unnecessary.

Done when: each field has its visible label as its accessible name; labels focus the intended input; invalid fields announce the problem; arrow-key selection is spoken and remains visible when the option list scrolls.

Evidence: webapp/src/components/RaceSetupEditor.vue:109–211; ui/FormRow.vue; ui/Combobox.vue; New race setup accessibility tree. Login’s explicit label bindings are a useful existing example.

P2 · 07

Cards give too many actions similar visual weight

Visual hierarchy · observed on setup library and dashboard

Observed → impact

Each setup card displays Start, Queue, Repeat, Edit, Duplicate, Template, and Delete. Running-server cards can show Edit setup, Race Control, Skip, Restart, and Stop together. Similar tinted outlines make actions compete. Headings are only slightly larger or heavier than metadata.

Proposed change

Make “Add to run plan” the library’s main action, with Edit alongside and less frequent commands in a labelled More menu. Keep Start as the idle-server action and Race Control as the running-server action. Preserve stop/restart in Race Control with existing consequence confirmations. Use one solid primary button per task region.

Done when: a participant can identify a card’s primary action without reading every button. Every relocated command remains keyboard-accessible and reachable in one menu opening. Confirm the chosen primary action with operators.

Evidence: webapp/src/pages/Events.vue:430–492; Dashboard.vue:359–431; ui/Button.vue. Seven library actions counted in the rendered page.

P2 · 08

Server context changes depending on where navigation starts

Navigation · code-grounded risk

Observed → impact

The Race Control sidebar link chooses the first running server (or the first instance) when outside a detail page. Run Plan keeps its own URL selection, and some Dashboard links go to bare /queue. Operators switching among multiple servers must re-check which one they are controlling.

Proposed change

Preserve a deliberate selection across Race Control and Run Plan, pass ?instance= from server-specific links, and place the server name in action labels and confirmation messages. Keep the overview clearly cross-server. If no selection exists, explicitly offer a choice instead of silently picking another server.

Done when: selecting Server 2 → Run Plan → Race Control → refresh/back retains Server 2; unavailable IDs produce a clear fallback. Verify this with at least two instances.

Evidence: webapp/src/App.vue:140–147; Dashboard.vue bare queue links; Queue.vue:49 already stores instance in the URL. This is a navigation risk, not evidence of an accidental server operation.

P2 · 09

The race editor asks users to understand the data model first

Form design · observed in the 448px setup sheet

Observed → impact

New race setup begins with group and optional name, then four required preset choices with adjacent New buttons, followed by drift scoring, lap override, and overflow strategy. Review is below the fold. The fixed narrow sheet limits room for explanations and a coherent summary.

Proposed change

Reuse the existing template system to fill the required presets. Lead with track and a recognisable saved template; keep individual preset editing available. Put optional overrides in Advanced, move group organization later, and offer a wider desktop editor with the existing preview beside it. Avoid forcing experienced users through a long wizard.

Done when: a new organizer can prepare a valid race from an existing template, explain what will run, and identify the destination server before saving. Existing preset editing and preflight warnings still work.

Evidence: webapp/src/components/RaceSetupEditor.vue:109–281; ui/Sheet.vue uses sm:max-w-md; existing PresetTemplates.vue and useRaceSetupPreview.ts. The shorter flow is a proposal to validate, not a measured improvement yet.

P2 · 10

Mobile works structurally but loses useful controls and space

Responsive UX · 375×812 inspection + source

Observed → impact

The bottom nav truncates Broadcast Display, and the More menu omits the desktop Sign out and theme controls. Race Control presents six mostly empty metrics before the circuit when stopped. Common buttons are 32–36px high; the toast close icon is smaller still. Queue instructions say “on the right” even when the panel stacks below.

Proposed change

Use short mobile labels, add account actions to More, and show a compact stopped-server summary before the next race. Use 44px as the product’s touch target, retain text labels for state, include safe-area padding, and replace directional instructions with named actions. Preserve table details in expandable rows when columns disappear.

Done when: primary flows work at 375px and 200% zoom with no lost actions or clipped focus; core touch controls reach the 44px design target. WCAG AA’s minimum target criterion is 24px with exceptions—32px is not automatically a failure.

Evidence: webapp/src/App.vue:293–390; ui/Button.vue; ui/Toaster.vue; Queue.vue:499–503. Mobile Race Control and More were inspected; account preferences contains no alternate logout/theme control.

P2 · 11

Missing, stale, and failed data need different recovery paths

Feedback · source-confirmed; network failures not induced

Observed → impact

Global errors disappear after eight seconds. ResultsHistory’s loader has no local catch or retry state, so failure can leave an empty or old view. The desktop connection indicator is a small titled dot. An offline stream occupies a full video tile even when none are live. Library search-empty copy suggests clearing filters but offers New race setup.

Proposed change

Use persistent inline errors with Retry, “No matches” with Clear filters, and “No sessions yet” with a role-appropriate next step. Keep last good data with a visible stale label. Show connection loss in text, separately from whether a server is running. Collapse unavailable streams; reserve toasts for transient confirmations.

Done when: initial loading, empty success, filtered-empty, partial failure, and disconnect/reconnect each have a distinct tested UI. A failed request must not imply there are zero records or that the server has stopped.

Evidence: webapp/src/stores/toast.ts:40; pages/ResultsHistory.vue:32–46; App.vue connection indicator; Events.vue:496–510; Dashboard’s observed 0/1 stream. Reference: Carbon empty-state patterns.

P2 · 12

History mixes data scopes and makes people choose an entry point

Information architecture · observed + source-confirmed

Observed → impact

Driver Stats, Session Search, and Results & History all appear in navigation. History’s filter changes sessions and result files but not the score request, so Best lap and Top drift remain global. Five summary cards use a four-column desktop grid. The observed page showed zero sessions beside a lap record with no scope explanation.

Proposed change

Label records “All-time records” and filtered totals “Matching sessions” first. Then test one Results & sessions entry with explicit Sessions, Records, and Files tabs; retain Drivers separately and preserve existing deep links. Use a balanced summary layout and put sortable, searchable results in consistent tables.

Done when: a filter’s scope is visible and consistent; global metrics are explicitly labelled; organizers can find a past session and a driver record without guessing between overlapping destinations.

Evidence: webapp/src/App.vue:109–115; webapp/src/pages/ResultsHistory.vue:35–40, 57–66, 107–136. Navigation consolidation is a hypothesis to test; scope labels are a direct fix. Table reference: Carbon data tables.

04 / Implementation plan

Fix the foundations. Then the flows.

Four reviewable increments. Reuse Vue, Tailwind, the existing stores, presets, and preview API. No framework migration is needed.

PHASE 01
2–3 days

Readable, accessible shared components

Findings 01, 02, 06. Update theme contrast and typography; fix Modal/Sheet naming, focus and dismissal; connect labels/hints; complete combobox semantics. Apply touch sizing to shared controls.

Files: style.css, ui/Modal.vue, ui/Sheet.vue, ui/FormRow.vue, ui/Combobox.vue, ui/Button.vue. Integrate with existing callers; preserve nested editor/picker behavior.

Exit check

Keyboard and screen-reader walkthrough of a nested race editor. Automated accessible-name checks plus manual focus testing. Contrast review in both themes; build and existing frontend tests pass.

PHASE 02
2–3 days

Trustworthy state and safe navigation

Findings 03, 04, 05, 08. Guard every draft dismissal. Align readiness/running labels. Make role-specific CTAs useful. Preserve selected instance across pages and put it into action confirmations.

Files: useUnsavedGuard.ts, App.vue, router.ts, Dashboard.vue, Queue.vue, ServerDetail.vue, SetupWorkbench.vue, editor callers. Reuse queue state rules and inspect backend semantics before naming interrupted events.

Exit check

Admin/steward/viewer × zero/one/two instances; stopped/running/repeating/stale fixtures. Unsaved field and group-only edits survive cancellation. No visible CTA silently returns to the same page.

PHASE 03
3–4 days

Clearer overview and race preparation

Findings 07, 09 and visual parts of 10–11. Reduce card action competition; promote contextual server state; collapse offline streams. Expand the editor on desktop, reuse saved templates, group advanced fields, and show the existing preflight summary beside inputs.

Files: Dashboard.vue, Events.vue, RaceSetupEditor.vue, PresetTemplates.vue, useRaceSetupPreview.ts, Queue.vue. Confirm template mapping and effective edited scope before changing save/restart wording.

Exit check

Prototype trial: choose the right server, prepare a race from a template, inspect a blocker, and queue it. Compare completion, errors, and time with the current flow before accepting navigation or primary-action changes.

PHASE 04
2–3 days

Mobile parity, recovery, and history clarity

Findings 10, 11, 12. Complete mobile account/navigation actions; expose hidden table details; add retry/stale/filtered-empty states. Label result scopes immediately; consolidate history navigation only after the task trial supports it.

Files: App.vue, ui/EmptyState.vue, ui/Toaster.vue, ResultsHistory.vue, SessionSearch.vue, stores/server.ts. Use existing request state rather than adding a parallel data layer.

Exit check

375/768/1024/1440px and 200% zoom; keyboard reordering; error/retry and dropped-connection fixtures. Verify production build, existing regression tests, and a final organizer/steward walkthrough.

Planning estimate: 9–13 focused engineering days for one developer familiar with the code, including implementation checks. Design decisions and participant scheduling may add calendar time. Re-estimate after Phase 02; this is not a delivery commitment.

Start with the smallest useful release

Ship Phases 01–02 as the first release. They address concrete access and task risks without waiting for the visual reorganization. Then introduce the revised overview and editor one route at a time.

Keep existing URLs and API contracts. Test disruptive commands against fixtures or an isolated test instance. Retain explicit confirmations for stopping, restarting, skipping, deleting, and editing shared presets.

Decisions to validate during delivery

  • Is queueing or immediate launch the most common library task?
  • Should Race Control remain a top-level entry or primarily a per-server destination?
  • Can existing templates supply all four presets without surprising shared-edit effects?
  • Does the API expose enough freshness to distinguish delayed telemetry from a stopped server?

Suggested formative study

Try the current flow and proposal with about five people spanning a new organizer, experienced admins, and stewards. Alternate the order to reduce learning effects. Combine automated accessibility checks with keyboard and screen-reader testing; neither screenshots nor a scan alone proves WCAG conformance.

06 / Research & evidence

The reasoning behind the proposal.

UX guidance was consulted before evaluating the flows. Product recommendations below are applications of that guidance to this repository.

Interaction principlesJakob Nielsen · Usability heuristics ↗

Applied system visibility, recognition, error prevention, and recovery to race status, presets, and action consequences.

Complex product UIIBM Carbon · Data tables ↗

Studied table toolbars, consistent rows, expandable detail, and contextual actions for the queue and history.

Feedback patternsIBM Carbon · Empty states ↗

Distinguish first use, filtered results, permissions, and system failures; provide a next action where useful.

Design foundationsAtlassian · Color foundations ↗

Studied semantic color roles and consistent themes. The proposal retains Server Manager’s blue identity and assigns color a clear purpose.

Accessible readingW3C · Contrast minimum ↗

Normal-size text requires 4.5:1, with criterion-specific exceptions. Measured current and proposed foreground/background token pairs.

Accessible controlsW3C · Target size minimum ↗

AA minimum is 24×24 CSS px or an applicable exception. The proposed 44px touch target is a stronger product convention.

Keyboard interactionWAI · Modal dialogs ↗

Focus entry, containment, Escape, accessible naming, and focus return inform the shared overlay repair.

Searchable selectionWAI · Combobox pattern ↗

Use explicit role, expanded state, associated popup, and active option semantics for the existing searchable preset picker.

Actionable validationGOV.UK · Error summary ↗

Connect a concise error summary to the exact fields that need attention, alongside inline error explanations.

Verified scope

What was actually reviewed

Read-only browser inspection of the local portal at localhost:3030, using its documented admin account: Login, Dashboard, Race Setups, new-setup sheet, Run Plan, Race Control, Admin, Server Setup, Results & History, and mobile More.

Desktop observation at 1280×720; mobile observation at 375×812. Keyboard reproduction in the setup sheet. Source tracing across navigation, shared UI, editing, toasts, readiness, queue state, and history. Existing source tokens supplied the light-theme contrast review.

Limits & confidence

What still needs validation

This is a focused expert review, not a full audit of every settings, content, broadcast, or driver-detail screen. Live racing, failed networks, screen-reader output, and non-admin accounts were not exercised; related findings are identified as source-based.

No server was started, stopped, restarted, or reconfigured. No race setup was saved. Light-mode portal appearance was not switched; the proposal includes both themes. The HTML mockup is illustrative and has no backend connection. User trials and accessibility verification belong in implementation.
